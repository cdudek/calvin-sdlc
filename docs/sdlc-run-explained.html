Your three moments

Three kinds of touchpoint, not three clicks. Acceptance repeats for each milestone and project. Blockers also come back to you.

Stage 5: one feature, one loop

The agent repeats this for every feature in a milestone. One go commits each feature; feature PRs add a verify and a PR. The hotfix lane uses the default branch instead.

Commits, not PRs

While a milestone is open, everything that belongs to it is a commit on milestone/<slug>. In the measured repo 13 of 22 PRs were docs-only records; this removes them.

A commit on the milestone branch

  • Features (the default, one-go)
  • Fixes found during the build
  • Test and flaky-spec repairs, CI timeout tweaks its tests need
  • Records: plans, handovers, gate lines, findings.md, validation.md, questions.md

A PR, and only these

  • The milestone PR, into project/<slug> or the default branch
  • The project PR, into the default branch
  • Feature PRs, only with delivery: "feature-prs"
  • Other repositories, and a change you send to the default branch first

No waiting on CI

Four rules keep the agent building while CI runs, and six CI rules keep CI fast. They hold for every stack; only the commands differ.

One real repo, one day: 39 CI runs, 22 failed, about 25 minutes each. 13 of 22 PRs were docs-only, yet ran the full pipeline.

B1

Records and fixes ride along

Plans, handovers, gate lines, findings, fixes and test repairs are commits on the milestone branch and ship in its one PR. No PR holds only a record or a fix. The archive move is the last commit of the PR into default.

C1

Gate only on real code

Wait for another PR only if this row's code needs something that exists only there. Then merge that branch locally and build on top. Otherwise build on.

C2

Never idle

After a push: arm auto-merge, watch in the background, start the next independent row. At most 4 builders. A red check interrupts; otherwise keep going.

C3

Touched tests only

A builder runs the tests its change touched. The full suite runs once per milestone, and in CI only where A5 says.

The CI blueprint, A1 to A6

A1

Per-step gating. Each step runs only when its paths changed, read from sdlc.json ciPaths; docs run nothing. One required check status still reports success.

A2

Production target. E2E runs against the built artifact, never a dev server.

A3

Shard. The slow suite splits over N jobs, each with its own database service.

A4

One retry. A pass on retry is reported. It fails only a full run.

A5

Full E2E where it counts. Inside the e2e step: the full suite only on PRs into default or project/*, and on milestone heads; other PRs run touched specs.

A6

Interior branches. project/* needs the same check, so auto-merge waits for green; milestone/* too with feature-prs. One go pushes straight to the milestone branch, so nothing merges into it.

Which paths run which step: ciPaths

Each repo lists its own paths in sdlc.json ciPaths, one list for the CI and for the agents that pick touched tests. One changes job reads them and sets a flag for lint, unit, build, e2e and deploy. A job runs only on its flag, and one required check always reports.

In sdlc.json, a TypeScript repo

"ciPaths": {
  "docs": ["changes/*", "*.md"],
  "all": [".github/workflows/*",
          "sdlc.json", "*.lock*"],
  "unit": {
    "include": ["src/*"],
    "exclude": ["e2e/*"] },
  "e2e": { "include": [...],
           "exclude": [...] },
  ...
}
  • A step runs for a file that matches its include and not its exclude. Globs are shell globs; * also crosses /.
  • A file that matches nothing runs everything, so a forgotten path costs minutes, never a missed check. Migrations are never excluded.
  • E2E scope is separate: the full suite only on PRs into the default branch or project/* and on milestone heads; other PRs run the touched specs (A5).
  • adopt writes the stack's defaults (TypeScript, Python, Rust, Rails, Kotlin, Scala) once and never overwrites them. ciPaths sits outside checks, so editing it needs no unlock.
  • A YAML counts as docs only if nothing reads it. Workflows, app config, k8s and terraform YAML are code.

Touched tests are the changed specs in the PR plus the tests of any module the diff touches. An empty set runs lint, types and unit tests only. One retry on CI: a pass on retry is reported, and fails the run only on a full run.

Every check ends in one of three lines

verify_gate.py runs the repo's checks in order and prints one verdict. The agent acts on it.

VERIFY PASS

All checks are green. The agent moves on to the next feature or stage.

VERIFY FAIL check=…

A named check failed. The agent fixes it and runs verify again.

VERIFY BLOCKED reason=…

The agent cannot decide alone. It stops and asks you.

not-approvedprotected-pathflakyno-progressscope-growthspec-conflicttest-proves-nothingunknown-verdictneeds-baselineallowlist-requestenv

What the agent may never do

Hooks and the lock file enforce edit boundaries. The runbook also limits scope, fix rounds and issue keys.

⊘

Write code outside /goalA hook refuses the edit.

⊘

Change the approved planFacts, "done" and checks are locked. Only your words can open them.

⊘

Edit a test to make it passA locked test stays as written.

⊘

Start a second fix roundRemaining milestone findings go to the next milestone. Remaining project findings go to the next project.

⊘

Decide scope for youTicket, size, kind and milestone are always your call.

⊘

Open a PR for work that belongs to an open milestoneFixes, test repairs and records are commits on milestone/<slug>. No PR holds only a record.

⊘

Wait on a PR your code does not needBuild on. If the code does depend on it, merge that branch locally and carry on.

⊘

Run the whole suite for one changeTouched tests only. The full suite runs once per milestone.

⊘

Close the ticket earlyIn a milestone, only its PR carries the change’s key. Feature PRs carry their sub-issue key.

How to use it

A repo needs adopt once. After that, start and continue with one command.

/cct:sdlc-run add dark mode

Start a new change. A Linear ticket id works too.

/cct:sdlc-run

Continue the change on the current branch, from wherever it stopped.

/cct:sdlc-run status

See open changes, their stage and their gates.

/cct:sdlc-run adopt

Set up a repo: config, verify script, hooks, and the stack's default ciPaths in sdlc.json. It checks your CI against the blueprint (step 8) and recommends the gaps. It never edits your ci.yml.

/cct:sdlc-run tracker

Choose or switch the tracker: Linear, GitHub, Beads or none.
