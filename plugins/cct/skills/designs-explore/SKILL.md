# Design mockups, generated by Codex with the design system

`/cct:designs-explore $ARGUMENTS` — `$ARGUMENTS` is what to design, in plain words:
`a pricing page for OMR Reviews`, `flow: agency onboarding`, `the empty state of the deal list`.

Codex generates the images from the design system and reference screenshots, and a plain
`gallery.html` on disk puts them side by side. Nothing is uploaded and nothing needs a server.

## Generated images, with the design system and references in

The owner decided (2026-10-06): mockups are **generated images**, made with Codex's
`image_generation` tool (`codex features list` shows it on). Not Codex-written HTML rendered
to PNG, not screens built from product code, not Figma, not low-fi.

What keeps an image inside the system is what goes in:

- **The repository's own design documents, by path, for Codex to read first** — whichever exist
  in the repo you are working in: `DESIGN.md`, `INTERACTION.md` and every page it routes to,
  `PRODUCT.md`, `AUDIENCE.md`, the glossary, and `docs/ux/setup.md`. Run Codex inside that repo
  (`--cd` a folder in it) so it can open them.
- **The design-system repository**: its GitHub URL and the token and component files, from
  `docs/ux/setup.md` or `cct:design-system-apply` (for OMR products, the OMR design system
  repo). Name it in the prompt; quote the tokens, do not leave Codex to guess them.
- **The design system in words**: every colour token with its hex and its meaning, the type
  scale (size/line-height/weight per role), spacing, radii, surfaces, control heights, and the
  anatomy of each component the screen uses (from the repo's DESIGN.md or token file;
  `docs/ux/setup.md` names it).
- **Reference images with `-i`**: screenshots of the product's existing screens that already
  follow the system (the closest page, a list, a card, a modal), plus the owner's annotated
  screenshots for this change. Two to six per run.
- **The spec for the screen**: its header, sections, columns, controls, the exact words, and the
  state, from `spec/screens.md` and `spec/interaction.md`.

Ask for a landscape image of a desktop window (1536 x 1024 or larger), one screen and one state
per image, real content, no lorem.

## Spec mode — the prototype of a design spec

`/cct:designs-explore spec <change-folder>` owns the prototype in `sdlc-run`: it runs in the
UX plan stage, and only when the plan marks the UI risky (a new pattern, a dense screen, a flow
nobody has drawn). It runs after the one `cct:ux-validate spec` pass and its fixes: images drawn
before the spec settles get redrawn after every spec fix (My Sampler, 2026-10-07: ~250 redraws).

0. **Validated spec, or stop.** Run:

   ```bash
   test -f <change>/spec/validation.md || echo 'spec not validated: run cct:ux-validate spec <change> once first'
   ```

   It prints: stop and run the one validation pass first. Exception: three directions on one screen
   (step 2) may come before validation; screen-by-state images may not.
1. Read `spec/screens.md`, `spec/interaction.md` (its state tables), `spec/ia.md` and the repo's
   design system (`docs/ux/setup.md` names it; run `cct:design-system-apply` or read the token
   file). The token rules go into every prompt.
2. If no direction is chosen yet, run Steps 2–6 on the most important screen first, three
   directions, and stop for the owner's pick.
3. **One anchor per screen.** Generate each screen's main state once. Check it yourself before
   anything is drawn from it; count repeated elements (cells, pads, rows, columns) on an enlarged
   crop (`PIL` `crop().resize()`), because 6 and 8 look alike at full size. Save it to
   `spec/prototype/refs/anchor-<screen>.png`.
4. **Every other state is an EDIT of its anchor** (`-i` the anchor; "change ONLY …" per image).
   Fresh redraws per state drift: grid counts, colours, header positions. A fix is an edit of that
   image, never a redraw. Output: `<change>/spec/prototype/screens/<screen>/shots/<screen>--<state>.png`.
5. **Image check loop, at most 3 rounds.** Reviewers (read-only agents) list only faulty images
   with their fix; edit those; check again. What is left after 3 rounds goes into
   `spec/prototype/known-image-faults.md` (the spec wins). A fault that is really a spec gap goes
   back to the spec and the validation re-check, then to the images. Then
   `gallery.py <change>/spec/prototype --open`; `spec/prototype/index.md` lists every screen ×
   state with its image and links `gallery.html`.

The PNGs are the baseline `cct:ux-validate build` compares the built app against.

## Step 1 — ask, unless you were told not to

Skip every question and go with the defaults when the request already answers them, or when it
carries **"do whatever"**, "egal", "mach einfach", "you decide", "surprise me". Say which defaults
you took, in one line, and start.

Otherwise ask once, with `AskUserQuestion`, at most these four:

| Question | Options (default first) |
|---|---|
| Surface | OMR product (design system binding) · OMR brand, not a product · Non-OMR / greenfield |
| Spread | Safe / Bold / Contrarian · By density · Three takes on one direction · By entry point (flows) |
| Output | Desktop and mobile · Desktop only · Mobile only |
| Theme | Light · Dark · Both |

The spreads are in `references/directions.md`. Never ask more than this — a fifth question buys
less than starting and iterating on something real.

## Step 2 — set the run up

```bash
RUN="design-explorations/$(date +%F)-<topic-slug>"
mkdir -p "$RUN"
```

Write `$RUN/brief.md`: what is being designed, for whom, the job it does, the constraints, and
**the axis the three directions differ on**. The gallery shows this at the top, so the reviewer
knows what they are being asked to decide.

For an OMR product surface, invoke `cct:design-system-apply` now and collect the token rules
into the brief. Do it before Codex runs, not after — retrofitting tokens into a finished layout
produces a design that obeys the rules and means nothing.

Folder shape, and the names matter because a reviewer refers to them out loud:

```
design-explorations/2026-09-12-pricing-page/
├── brief.md
├── gallery.html
├── 01-safe/     prompt.txt · notes.md · shots/<screen>--<state>.png
├── 02-bold/     …
└── 03-contrarian/
```

Flow mode makes one image per step: `shots/01-choose-plan.png`, `shots/02-add-team.png`, … The
gallery shows every image, so a flow is compared step by step across all three directions.

## Step 3 — three Codex runs, in parallel

Assemble each prompt from `references/codex-brief.md` and the "Generated images" section above
(the design system in words, the spec of each screen), write it to `$RUN/<NN>-<slug>/prompt.txt`,
and run Codex with the reference screenshots attached: `codex exec … -i <ref1.png> -i <ref2.png>
- < prompt.txt`. The prompt tells Codex to GENERATE the images with its image generation tool and
save each into `shots/`, plus `notes.md`. Run the three **as parallel background shells** and wait.
One run per direction, never one run for all three — a single pass converges them.

The call, the file checks afterwards, and what to do with a direction that comes back wrong are
all in `references/codex-brief.md`. Read it before the first run.

## Step 4 — look at every image

Open each image. A screen that breaks a token, uses a component the system does not have, gets a
word wrong or is cut off is re-generated with the fault named in the prompt. `render.sh` is only
for the rare run where someone explicitly asked for clickable HTML.

## Step 5 — gallery

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/skills/designs-explore/scripts/gallery.py" "$RUN" --open
```

Writes `$RUN/gallery.html` and opens it. Each direction gets its screenshots, a link to the live
HTML, its one-paragraph rationale, and a feedback box. **Copy all feedback** puts every box on the
clipboard; the reviewer pastes it back here and you run the next round.

The feedback is not stored anywhere. That is deliberate: persisting it needs a server, and a
design review that stops working when a server goes away is not a design review.

## Step 6 — hand it over

Report the path, the three names with one line each, and what they actually differ on. Then stop
and wait. Do not pick a winner, do not start building one, and do not offer a fourth.

## What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| An image ignores the system or looks like another product | No design documents or reference screenshots in the run | Re-run with the repo's DESIGN.md / INTERACTION.md / PRODUCT.md paths and 2–6 product screenshots attached with `-i` |
| All three look the same | One Codex run was asked for all three, or the spread was not stated | One run per direction, and put the axis in `brief.md` |
| Tokens ignored on an OMR surface | `design-system-apply` ran after Codex instead of before | Re-run the direction with the token rules in the prompt |
| Playwright missing | not installed on this machine | `pip install playwright && playwright install chromium` |

## Scope

This skill explores. It does not build, and it does not decide.

Once a direction wins, implementing it is ordinary work — `cct:design-system-apply` for OMR
frontends, `cct:vue-code-write` for `omr-js` consumers. Critiquing what was built afterwards
is `cct:ux-audit`. Getting Claude rather than Codex to draft quick variants, with no
rendering and no gallery, is `cct:variants-create`.
