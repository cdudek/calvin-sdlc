# The SDLC: how work moves through this repo

This repo follows the AI-native SDLC on the milestone process: the agent drafts, the engineer
confirms twice, and everything after runs inside `/goal`. `cct:sdlc-run` drives it from
`sdlc.json`. GENERATED by `sdlc-run adopt` — edit `sdlc.json` and re-run, or edit the
Repo-specific section below.

```
{{CHANGES_DIR}}/<date>-<KEY>-<slug>/
  decisions.json        ticket · design · size · kind · milestone
  intent.md             ## Asks, job stories, success measure
  spec/                 the UX plan: brief · ia · interaction · screens · conformance · validation
  facts.md              EARS facts citing asks, screens and test tags
  plan.md               where things go · feature PRs · Done · Goal handover
  done.json, lock.json  the criteria as data, and their hash at approval
  milestone.md          features and states · outcome
{{DESIGNS_DIR}}/
  INDEX.md              one line per design and decision, generated: read this first
  <date>-<type>-<slug>.md   a design, or one decision (type adr) with status and supersedes
```

A decision is a file of its own, never a row appended to a log. A design says what is true
now and is edited in place. After adding or changing either, run
`python3 scripts/design_index.py write`; the guardrail test fails on a stale index.

## Stages

| Stage | What happens | Touchpoint |
| --- | --- | --- |
| 1 Intent | One dialog (ticket, design file, size, kind, milestone); asks verbatim; the agent drafts `intent.md`. | engineer confirms intent |
| 2 UX plan | `omr-ux` design, sitemap, conformance, words; one validation pass. Skipped for size `none` or `ux: off`. | none |
| 3 Facts | Facts cite asks, screens and the E2E tag that proves them; plain-language lint. | none |
| 4 Tech plan | Where things go, milestones and their features, Done, one goal for all of it. | one gate for all three, then `verify_gate.py approve` |
| 5 Build | One go (default): one `/goal` builds every milestone in order; per feature, tests, build, commit, and nothing else runs between features. Questions go to `questions.md` and never block; answers become asks of the next milestone. (`delivery: feature-prs`: a PR per feature.) | none |
| 6 Milestone | Checks on the milestone diff; the full E2E suite once, ×3 only for changed and flaky specs (see Build and test); validation of every fact and ask against the built app (`validation.md`), one findings list, one fix round, `verify_gate.py milestone`, one PR that releases it. | only when a Critical or High would be deferred |
| 6p Project | Only for work spanning several milestones: rebase `project/<slug>`, re-check the whole project diff, one PR to the default branch. | engineer accepts |
| 7 Outcome | Archive on merge; read the success measure after release. | engineer reads it |

### Branches

```
<default> ─── milestone/<slug> ─── <feature branches>            one milestone
<default> ─── project/<slug> ─── milestone/<slug> ─── <features>  a project
```

A project branch exists only for work that spans several milestones. One milestone needs
none.

## Build and test

After the one gate, `python3 scripts/verify_gate.py approve <id>` locks the criteria. One
`/goal` from `plan.md` `## Goal handover` then builds every milestone. Each milestone ends on
one line from `python3 scripts/verify_gate.py milestone <id>`: `VERIFY PASS`, `VERIFY FAIL`
(fix and rerun) or `VERIFY BLOCKED reason=<code>` (stop and ask the engineer).

For a bug, commit the failing test first and set `testLocked: true`. While locked, test files
matching `testGlobs` cannot be edited unless `testEdit` records the user's OK.

For milestone E2E, use the committed `e2e/flaky-specs.txt` list. The installed
`cct:e2e-test-run` reference `suite-speed-and-reliability.md` section G defines the
selection and line format. Section F defines the lock and load policy for shared machines.

## Ask resources

Every image, screenshot, feedback-tool session, recording or file that came with an ask is
copied into `{{CHANGES_DIR}}/<id>/asks/<source-date>/` and linked from the `Resources`
column in `intent.md`. Links in the change folder stay inside the repo. `sdlc.json`
`feedback` contains repo paths or globs only.
Run `marks.py init <id>` for Snapmark/reference images; fill `marks.json` against fresh headless shots in `verify/shots/`; milestone `owner-marks` checks it.

## Tiers: Ship / Show / Ask by blast radius

`.github/tiers.json` decides the tier by path.

**Only the PR into the default branch is tiered or reviewed.** A feature PR into
`milestone/*`, and a milestone PR into `project/*`, are interior merges inside one change:
they auto-merge on their checks alone, with no Claude review and no code owner. Both
workflows check the PR's base ref themselves, so this holds for a hand-opened PR too.

| Tier | Paths | Who looks |
| --- | --- | --- |
{{#ASK_GATES_MERGE}}
| **ask** | {{ASK_PATHS}} | a code owner before merge |
{{/ASK_GATES_MERGE}}
{{#ASK_MERGES_ON_GREEN}}
| **ask** | {{ASK_PATHS}} | highest blast radius; read it, but it does not gate merge |
{{/ASK_MERGES_ON_GREEN}}
| **show** | {{SHOW_PATHS}} | the co-owner after merge{{SHOW_CHANNEL_NOTE}} |
| **ship** | everything else | nobody |

`show` and `ship` auto-merge when required checks are green. The App token arms auto-merge,
never `GITHUB_TOKEN`.
{{/TIERS}}
{{#NO_TIERS}}
## Merging: auto-merge on green

One owner, so no tiers (`sdlc.json` `tiers: false`). Every PR merges itself once it is green.

- **Arm it:** `gh pr merge <n> --squash --auto`.
- **What it waits for:** required checks on `{{DEFAULT_BRANCH}}`.
{{/NO_TIERS}}
