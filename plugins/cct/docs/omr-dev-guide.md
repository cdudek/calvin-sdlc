# omr-dev skills — interface contracts

Loads for every skill in this plugin. The review/fix skills (`pr-review`, `review-fix-loop`, `address-feedback`) and the agents under `../agents/` pass data **by convention, not by enforced code**: one file *produces* a JSON shape, a section marker, a handoff variable, or a spawn-prompt label, and another file *consumes* it by name. Nothing checks the match at runtime, so producer and consumer drift silently.

**Rule when changing or designing any interface here: change a producer's shape → update every named consumer in the same edit.** These contracts **cross skill boundaries** — a field minted by an `agents/*` reviewer flows through `pr-review` scripts into `review-fix-loop` and `address-feedback` — so the consumer you must update is often in a different skill or in `../agents/`. Grep the field/marker/var name across `skills/` and `agents/` before you ship the change.

Field rules that have bitten before:

- `validation_effort` is an **integer 0-6** everywhere — the producer (`code-reviewer.md`) and consumers (`merge.md`, `validate-prep.sh` numeric sort, `validate-agent.md` drill-cap thresholds) must all use the int scale; a string enum crashes the sort.
- `side` (`RIGHT`/`LEFT`) is **not** emitted by `code-reviewer.md` or `merge.md` despite sitting in the field list above — `posting-findings.sh` mints it (hardcoded `RIGHT`). From there it must survive the whole posting chain (`posting-findings.sh` → `reconcile-threads.md` → the create-thread scripts), which require a non-null `DiffSide` on every new thread.
- `unverified` (per-finding, from `code-reviewer.md`) is **not** in the canonical `findings.json` schema — it is a `pr`-quick render hint only; the validated lanes drop it on serialization. Don't add it to the schema.
- **Branch-name handoffs are validated at mint time, never escaped.** `$BASE`, `$BASE_BRANCH`, `$TARGET_BRANCH` and the loop's `review_base` all end up in two places: an LLM prompt, and a `git` command line. Escaping is wrong for the second — `git diff feat&amp;x...HEAD` is not `git diff feat&x...HEAD`, so an escaped value silently reviews the wrong range. But `git check-ref-format` **accepts** `<`, `>` and `&` in a ref name (verified: `a<established_decisions>b` is a legal branch), so an unescaped one can forge a fence tag inside a prompt. The resolution is neither: whoever mints one of these variables rejects a ref name outside `^[A-Za-z0-9._/+-]+$` and stops with the offending name, before it reaches any prompt or any `git` invocation. Downstream consumers then pass it through byte-exact and add no escaping of their own. (This does not apply to the *fenced* blobs — `git log` output, user commentary — which are multi-line untrusted text and keep their `&`→`&amp;`, `<`→`&lt;` treatment.)
- `source` (`claude` | `codex` | `both`) is minted by **two** producers and assigned by a third: `code-reviewer.md` always emits `claude`, `codex-review.sh` always stamps `codex`, and only `merge.md` may set `both` — by collapsing one of each onto the same root cause. That collapse also raises `confidence` (`merge.md` → Provenance); `synthesize.md`'s own Deduplicate step must not raise it a second time. A run with no Codex pass still carries the field, uniformly `claude`, so no consumer needs an absent-field branch.
- **The probe fields are Claude-only.** `executable_claim` / `probe_kind` / `probe_pattern` / `probe_input` are emitted by `agents/code-reviewer.md` and never by `pr-review/scripts/codex-review.sh` — they are absent from `codex-findings-schema.json` on purpose, because the Codex pass runs read-only and does not probe. A Codex finding therefore never carries them, and merge must not synthesise them. (Same shape of caveat as `side` above: the field list names every field that flows, not every field every producer mints.)
- **`executable_claim` findings carry a four-field group, or none of it.** `executable_claim: true` is meaningless without `probe_kind` / `probe_pattern` / `probe_input`, because `pipeline-tail.md` has nothing to reproduce — `merge.md` must carry the group intact through a collapse. The probe is run by the **orchestrator** via `probe-pattern.sh` and reaches `validate-finding` as an observed result on the `Probe:` line. Do not move execution into the validator: it holds `tools: Read` deliberately, because its entire input is attacker-controllable text from the diff. Do not extend the probe to running the artifact under review either — that is arbitrary execution of untrusted code, and a claim needing it stays `unverifiable`.
- **`severity` gates posting, and `posting-findings.sh` is where.** Only `confirmed` findings at `suggestion` severity or above become review threads; `nit`, `unverifiable` and the demoted appendix never leave for GitHub. That one filter covers all six pr paths, so do not re-add a second one downstream — and do not relax it in `reconcile-threads.md`, which receives the array already filtered. `pr-quick` is the sole exception: it writes no `findings.json`, cannot run the script, and restates both exclusions in its own file.
- **`severity` also gates the fix loop, and `fix-handoff.sh` is where.** It routes a confirmed finding to `fix_now` only when the finding blocks the verdict — severity above `suggestion`/`nit`, or `reversibility: entrenches` at any severity — and to `discuss` otherwise. The two filters are deliberately different: posting decides what a PR author is made to read, `fix-handoff.sh` decides what an autonomous loop is allowed to change. Neither drops a finding; both leave it in `findings.json` and in the report. The severity test in `fix-handoff.sh` is **inverted** — it names the two severities that do not block — so an unknown value routes to `fix_now` instead of being silently demoted.
- **`reversibility` gates blocking independently of `severity`.** A confirmed `entrenches` finding floors the report verdict at `fix-first` at any severity (`pr-review/references/report-sections.md` → Verdict, derived in `role-code-analysis/references/synthesize.md`). Producers judge the cost of *undoing*, not of doing; a consumer that collapses the two axes loses the only signal that stops a cheap-now shortcut being deferred until it is expensive.
- **The Codex sanitize chain is fail-closed, and that is the contract.** `codex-scan-secrets.sh` owns the secret-filename patterns (one source; its `find` walk, its `--match-names` mode and the rsync excludes all read the same list), withholds **every symlink** whatever its name, and exits **non-zero** on any root it could not fully walk; `codex-review.sh` refuses to run Codex unless the scan succeeded, the `rsync` mirror was built, a post-copy self-check confirmed every withheld path is absent from it, and — in diff mode — `codex-filter-diff.sh` removed the sections of secret-shaped files from the diff it embeds (the mirror cannot protect text that is already in the prompt). An empty scan result must always mean "nothing secret-shaped is here" and never "the scan did not run" — under this design the scan output *is* the exclusion set, so a silently empty result ships the files it exists to withhold. Never add a fallback that passes `$ROOT` to `codex exec`; withholding by absence is the only control, because `--sandbox read-only` constrains writes and the exposure is a read.
- **The acceptance-criteria audit is a two-file contract, and both files fail loud.** `ac-gate.sh` writes `ac.json` — `{mode:"ac",source,criteria:[{id,text}]}` or `{mode:"none",reason,detail?}` — by pure text extraction from `INPUT.md`, so the gate answers identically on every resume. `ac-check.md` then spawns `ac-auditor`, which grades **exactly** the criteria in `ac.json` and returns `ac-coverage.json` — `{ac:[{id,text,status,evidence:[{file,line,quote}],note}]}`, one row per criterion, same ids, same order, same count. The orchestrator runs six checks before writing the file — row count, ids, statuses, each row's `text` against `ac.json`, at least one `evidence` entry on every `covered` row, and `scripts/ac-verify-evidence.sh`, which opens each cited file and confirms the quoted text is in it — and any failure is an audit failure, never a partial grading: a dropped criterion renders as a criterion nobody objected to. The checks cover content and not just shape because a criterion, unlike a finding, gets no independent validator. **`evidence` carries a quote for exactly that reason**: a bare `file:line` cannot be checked against anything, so a fabricated `covered` citing an unrelated place passed every shape check there was. What stays open is relatedness — that the quoted code has anything to do with the criterion — and only a validator per `covered` row closes it. A failed audit writes **no** `ac-coverage.json` (so the next run retries) and sets `$AC_MODE` to `none` with `$AC_REASON` `audit-failed`. `report-sections.md` renders the Acceptance criteria section in **both** states — the five `none` reasons each get their own wording, because `unresolved` and `audit-failed` ask for a re-run while `no-reference` and `not-applicable` do not. `synthesize.md` step 9 floors the verdict at `fix-first` on any `missing` or `partial`, and also on `$AC_REASON: audit-failed` — the four other `none` reasons mean nothing was there to grade, while `audit-failed` means the grading could not be trusted, and that state is reachable from the ticket text. `not-verifiable` never floors it.
- `fix-set.json` carries a **projection** of the finding fields — `{id,file,line,severity,dimension,body,reversibility,idiomatic_fix?}` — written by `agents/extra-validation-runner.md`, read by `address-feedback/commands/fix-set.md`. Change one side → change the other in the same edit. `reversibility` and `idiomatic_fix` are carried for **reporting**, not for routing: the fix stage still applies the minimal change, and `review-runner` is always nested so the report's verdict and its `entrenches` marker never render inside a loop run — this projection is the only path by which either fact can reach a human.

**Env-var rule for script paths** — a file in **skill context** (`SKILL.md`, `references/*.md`) references a script as `${CLAUDE_SKILL_DIR}/scripts/<name>.sh`; a file in **agent context** (`agents/*.md`) must use `${CLAUDE_PLUGIN_ROOT}/skills/<skill>/scripts/<name>.sh`, because `${CLAUDE_SKILL_DIR}` is undefined when an agent runs. Don't "normalize" an agent's `${CLAUDE_PLUGIN_ROOT}` path to `${CLAUDE_SKILL_DIR}` — that breaks it.

## State layout

`$STATE_DIR = $STATE_BASE/rev-<revid>` (per revision); cross-iteration accumulators (`discuss.json`) live in `$STATE_BASE`. See `pr-review/references/state-dir.md`; `scripts/state-dir.sh` computes and creates the dirs.
